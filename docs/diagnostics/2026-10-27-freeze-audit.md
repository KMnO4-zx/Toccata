# 2026-10-27 卡死排查

## 现场与结论

- macOS 26.6.2，Toccata 0.0.9（14）。18:45 的系统报告记录约 115 秒无响应，CPU 平均 94%。
- 20:56 再次抓到最新开发构建的现场；用户确认最后操作是展开子任务。进程启动约一分钟后即出现问题，并非必须长时间运行才触发。
- 5 秒 `sample` 中，主线程的 3,736 次采样全部在 SwiftUI 更新链上，包含 `TasksView.HierarchyListItem`、`LazySubviewPlacements`、`LazyStack.place` 和原生子任务拖动柄更新。约 3,395 次经过 `GraphHost.flushTransactions`；还存在悬停更新。
- 这次是任务列表的布局计算持续占用主线程。没有证据将本次现场归因于数据库、socket 等待或事件监听器泄漏。悬停可能参与反馈，但没有被单独确认为根因。

现场文件保存在本机临时目录 `/private/tmp/toccata-hang-86555.txt`；旧系统报告位于 `/Library/Logs/DiagnosticReports/`。报告与线程采样未上传。

## 本轮处理

1. `TasksView` 改用普通 `VStack` 计算已展开任务树的布局，绕开现场中持续运行的懒布局高度估算；保留统一任务身份、完成状态、展开动画和键盘导航。
2. 工作台日历的当天列表、未安排日期列表，以及状态栏日历具有相同的动态子树和原生拖动柄结构，同步移除这三处 `LazyVStack`。这些入口是按相同机制处理，未声称都已现场复现。
3. 工作台日历使用现有 `StableWidthScrollView`，固定预留滚动条空间，避免任务数量变化改变日历宽度。
4. Rust IPC 连接在注册前设置 250 毫秒写超时。写入失败时关闭连接的两个方向并移除订阅者，唤醒持有克隆连接的读取线程，避免它继续占用资源。广播仍按顺序发送，多个慢订阅者的等待可能累加；该超时不是所有客户端共享的总截止时间。

普通栈会布局当前范围内的全部可见树节点，成本随节点数增长。此次取舍优先保证展开过程稳定；不能据此宣称任意规模的任务库均已完成性能验证。

| 键盘动效 | 键值限定 128 个，每键最多 4 个气泡，过期清理；离屏断开订阅。 |
| 语言切换 | 取消旧的过渡任务，延迟后再次检查取消状态。 |
| 活动、应用排行、热图刷新 | 数据库查询在后台；单次进行中查询加一次待刷新请求，避免刷新任务无限排队。 |
| 分享图生成 | 禁止并行生成，取消后不发布旧预览，像素数量有上限。 |
| 主线程任务数据库写入 | 事务的锁等待上限 1 秒，应用内单主 actor 写入；未发现永久互等。大量数据和异常磁盘延迟仍属于独立性能边界。 |
| 后台进程停止 | 异步检查退出，有 6 秒上限和取消处理。 |
| 本地连接探测 | 实测 macOS Unix socket 接受队列满时连接立即失败，未复现阻塞，因此没有按原先猜测修改。 |

额外确认：Rust 事件广播原来在持有订阅者锁时执行无超时写入。停止读取的订阅者会拖住事件写入、持久化与退出，属于独立于此次 UI 布局现场的阻塞路径。真实 Unix socket 回归在旧实现中 2 秒超时失败，修复后能剔除慢连接、结束其读取线程，并向正常连接完整发送 2 MiB 测试消息。

以下仅为优化候选，本次没有作为已确认的卡死原因修改：菜单详情定位重复调用 `setFrame`；切页后已有后台查询可能完成一次；主线程已经卡住时实时事件暂存队列可能增长。最后一项会放大卡死后的内存占用，不能倒推它是这次卡死的起因。
